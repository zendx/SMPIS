## Phase 4: historical evaluation and operation

| Capability             | Current behavior                                                                                                                                                                                                                     | Remaining work                                                                                                                                                                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Multi-school operation | Platform operators can provision isolated schools with their own administrator, currency, calendar and accounts. The Schools page provides aggregate counts. Tenant administrators cannot access other schools or provision schools. | No shared user membership/switcher across schools: accounts currently require unique email addresses. Campuses are represented as separate school workspaces; hierarchy, group-wide finance and cross-campus transfers are not implemented. |
| Enrollment history     | First enrollment counts by month, excluding transfers from new-enrollment counts                                                                                                                                                     | Withdrawal/re-enrollment cohort history needs additional historical data modeling.                                                                                                                                                          |
| Revenue planning | Live complete-month receipts and six-month mean baseline; optional historical CSV; mean, seasonal and damped-trend candidates compared on a tuning window and separate final six-month holdout | Advanced estimate is stored only if held-out MAE beats baseline by at least 5%; it remains review-only and is not a production forecast. The live page still displays the simple baseline when eligible. |
| Student support | Pseudonymous historical CSV, fixed academic features, temporal train/tune/test sets with outcome-overlap purging, regularized logistic candidate, Brier/calibration/precision/recall evidence against a prevalence baseline | Requires at least 100 train, 30 tune and 30 test records and minimum class counts. Aggregate evidence only; no student-level score or automated intervention. |
| Parent retention | Pseudonymous historical data and temporal evaluation with attendance, arrears ratio and satisfaction features; one observation per family prevents repeat-family leakage | Outcomes follow feature dates. Review-only. No churn score is active. The school has supplied no authentic historical data. |

The first administrator created through a fresh installation's setup becomes its platform operator. Existing installations require an explicit operator designation with the local `scripts/platform-operator.js` command. New school administrators never receive that designation automatically. Platform access shows portfolio summaries; it does not impersonate tenant users.

## Phase 1 follow-ups delivered in this increment

- MFA recovery: ten one-use codes, stored as hashes, regeneration invalidates previous codes, password confirmation, login verification and audit events.
- Class batch billing: idempotent invoice creation, per-student results and failures, preserving individual invoices and concessions.
- Attendance summary and chronic-absence reports, with class filtering for student/register attendance exports. These use recorded days and the configured attendance threshold; the minimum sample for chronic absence is three days.
- Paystack checkout preparation, payment verification, raw-body HMAC webhook verification, duplicate-credit prevention, school-specific keys, test-mode separation and a reconciliation status for captured funds exceeding a changed invoice balance.

Still outstanding from the initial Phase 1 scope: multiple guardian relationships/accounts per child, custom role editing, public applicant document uploads/photos, working-day/holiday attendance policy, staff early-departure rules, device integrations, refunds/adjustments and post-invoice concessions, programme/fixed-amount fees, installment allocation, broader operational load/recovery testing and storage encryption configuration. These have not been erased by starting later phases.

## Integration and deployment status

Paystack request/verification/webhook behavior is tested with a local fake provider. No Paystack account was contacted or charged. TEST-mode confirmations never credit real invoice balances. LIVE mode requires an explicit environment switch and a per-school secret. Captures that cannot be applied safely are retained as REVIEW for finance reconciliation; automated gateway refunds are not implemented.

Hostinger VPS files provide Node, PostgreSQL, Caddy/HTTPS configuration, persistent data and backup volumes, and a readiness endpoint. The Compose configuration has been parsed locally. Docker Desktop's engine is not running here, so a container build and external PostgreSQL integration have not been verified. No server purchase, DNS change, upload or deployment has been performed. See [PRODUCTION-HOSTINGER.md](PRODUCTION-HOSTINGER.md).

## Verification

`tests/operations.test.js` covers workflows, tenant isolation, survey amendments, HR documents, leave calendar/cancellation, review revisions, model-data scope, forecasts, Paystack and MFA. `tests/models.test.js` exercises temporal gates with synthetic fixtures, never stored as real school data. `tests/operations-browser.mjs` exercises real Chrome journeys for staff, parent and administrator, plus desktop/mobile screenshots. The core and academic test suites remain regression checks; all test data stays in isolated in-memory databases.

The last full API integration run on October 2, 2026 passed **48 tests**, including transfer/report revisions, rosters/policies, exam conflicts, HR uploads, leave rules/cancellation, survey publication and model evaluation. The production build passed. Minor permission and enrollment-migration changes followed on October 3 and have not been through another suite run. New screens have no dedicated browser run. Hostinger, live Paystack, SMTP, external PostgreSQL, real-data model performance and production load remain unverified.
